# One-click private video draft (incremental delivery)

The **Generate draft video** action in a saved YouTube production now:

1. Locates only that production's completed YouTube script (other destination drafts are independent).
2. Refreshes its saved storyboard, preserving unaffected scene edits and backing up the previous document before any overwrite.
3. Compiles a renderable Director plan without requiring script or scene-plan approval. Unsupported factual claims are draft warnings, not publishing clearance.
4. Opens the actual production controls with an automatic-start intent. Preflight starts immediately. If a voice, consent, FFmpeg or Chromium requirement is missing, the corresponding setup stays visible with a retry action.
5. Submits the real render's dependent stages to the Rust Jobs scheduler before starting TTS or media work. The renderer records state transitions through the local worker endpoints and can be cancelled. The same jobs appear in Jobs and their IDs are linked from Director.
6. If **Search free scene media** is enabled, records an `asset-search` Jobs node after browser preflight. It sends bounded scene-subject searches to Poly Haven and Openverse, stores metadata-only ranked suggestions in the job-owned output folder, and shows them again in Director → Find the right visuals. Pexels API search/download is disabled; the creator can import a JPEG or MP4 downloaded from its website for the selected scene. Search errors fall back to Kumiki visuals without holding narration hostage. Downloads and scene selections still require the editor's explicit per-asset rights review.
7. On a later draft with reviewed Pexels scene selections, validates pinned local JPEG/MP4 bytes, hashes, provenance, path containment, and H.264 footage metadata before narrator synthesis, then freezes them into render-owned content-addressed files. Existing Kumiki general scenes display selected photographs with cinematic motion or silent frame-synchronized footage. The local capture server serves only the frozen files and supports MP4 byte ranges; invalid or changed selections fail with a clear action, not a random substitution.
8. Shows rendered-frame progress and, on success, the playable MP4 with direct MP4, SRT caption, and renderer-captured cover-frame PNG downloads. The cover is not presented as a designed thumbnail. It never publishes automatically.

## Runtime dependencies

The local Rust server on `127.0.0.1:8787` must be running; production jobs intentionally fail closed if persistent tracking cannot be created. Override only with a loopback `CONTENTGEN_JOBS_ORIGIN`. The Node renderer uses its existing Chromium, FFmpeg and authorized Fish/local TTS integrations. Provider credentials must not be persisted in Jobs.

Worker transition routes are `POST /api/jobs/{job_id}/nodes/{node_id}/{start|succeed|fail}`. They are local-process-only; they validate the bound job/node and reject Origin-bearing browser requests. The Rust scheduler serializes transitions in SQLite. On server restart, its existing orphan-reconciliation routine marks interrupted attempts failed rather than presenting phantom running work.

Completed Jobs nodes now retain **bounded content-identity ledgers** alongside their attempt history: the reviewed scene-media selection fingerprint, per-scene photo/footage hashes and type, verified narration beat hashes and sample counts, the mixed master-audio hash, plan/build hashes and contiguous encoded scene-segment hashes, final MP4/caption/cover hashes, and the published render-manifest hash. The hashes are calculated from actual generated or previously verified bytes; the adapter validates SHA-256 shapes and step ownership before persisting and removes filesystem paths, unrecognized fields, and third-party media-search warning strings. Jobs can therefore inspect which artifacts an interrupted worker really finished. **A ledger is evidence, not a claim that the corresponding node has an independent executor or that a missing artifact is reusable**: retry still validates the actual owned cache and can regenerate missing content. The final package is only recorded after the release is committed.

## Current scope and limitations

### Per-scene review evidence and remaining verification

The full MP4 exporter now requests a deterministic Chromium-captured review still from **every narrated scene**, in addition to the opening and final frames and a post-payoff sample. It refuses to silently omit a chapter: missing/out-of-order/changed stills, invalid scene boundaries, more than **64** selected stills, or **256 MiB** of aggregate screenshot bytes fail the draft before a release is published. Each copied PNG is SHA-256 checked against the renderer's output. `render-manifest.json` and `qa-report.json` contain `visualCoverage`, including a specific review still per chapter, declared stock-video/photo/Kumiki source counts, and the IDs of scenes without stock video. The manifest also records a digest for `qa-report.json`; the local Studio serves the report only if the bytes match this digest. The Export panel makes the coverage counts and verified report visible alongside the MP4, including after reopening a saved draft. These are **sampled frames**, not continuous visual assessment; a human must still watch the entire narrated video and inspect licensing/provenance.

**Still missing:**

- A full interactive browser demonstration that edits a scene, starts the draft without extra clicks, completes authorized speech, and watches the resulting full FFmpeg-encoded MP4. Headless/mocked handoff tests do not substitute for this proof.
- Guaranteed rich, appropriately licensed *footage* in every scene. Auto-prepared CC0 still photos and authored Kumiki scenes are useful fallbacks, but this report intentionally counts those as **without stock video**. A media match is not an approval of identity, releases, aesthetics, or rights.
- A live Rust/Node process-restart drill across heartbeat expiry and provider uncertainty. Recovery behavior is covered by simulations and unit tests, but requires a Cargo-equipped environment and controlled TTS authorization to verify externally.
- **Durable voice registry and cast integration (project + character + saved scene storage implemented):** Project favorite Fish/local voice IDs, editable gender/situation/language tags and primary/secondary priority have SQLite migration `0019` and revision-checked `GET/PUT /api/project-voices/{project_id}`. Immutable Character Studio ZIP revisions have SQLite binding registry `0020`, validating every mapped draft ID/character/revision before saving. **New migration `0021`** adds a bounded, revision-checked `GET/PUT /api/scene-cast/{project_id}/{source_plan_sha256}` registry for explicit scene speaker/voice assignments, scoped to the original compiled script/storyboard. It rejects duplicated shots, inconsistent character identities, malformed providers/IDs and stale edits, and preserves deliberately empty casts. The embedded Director now automatically migrates an intact browser cast when no server entry exists, restores an existing cast by reapplying validated `/edit` revisions, and requires an explicit choice on divergence; failed sync preserves local edits and blocks full-video auto-start instead of discarding characters. Vite forwards all three APIs to Rust without rewriting loopback Host/Origin. The Fish ID `6ab4c6b0f37f4243a99046478647be94` remains primary. Consent and credentials are never stored in these registries. **Still missing:** live cross-device/browser and Cargo-backed API verification; robust reconciliation of *all* non-cast scene edits across devices; project-deletion server cleanup; voice rights/provider checks and actual approved multi-voice synthesis. The Rust integration tests are authored and a disposable SQLite table/CAS test runs; actual Rust compilation remains unverified here because Cargo is unavailable.
- **Saved character voices and mixed-speaker videos:** revision-pinned character→voice metadata and explicitly authored scene-cast mappings have separate SQLite registries. The embedded Director now offers a **Conversation + narration** scene editor with two to sixteen ordered speech turns, stable IDs, character/narrator selectors, per-turn saved voice IDs and pauses. A one-click **Conversation + narration video template** loads the synthetic demonstration without model setup, preserving its factual-source-linked narration while adding editable Pip and Quill starter lines to the middle visual scene. The second character starts with the same Fish voice ID (`6ab4c6b0f37f4243a99046478647be94`) until the user chooses another voice; the sample does **not** claim to provide two different natural voices. The original scene remains one continuous visual chapter; FFmpeg measures, concatenates and caches each spoken turn separately, leaves authored silent pauses, and emits speaker-labeled scene-timed SRT cues. **Pip and Quill animation slice:** landscape/portrait export includes two distinct original, local vector puppets using the existing deterministic character evaluator (head/torso idle, seeded blink, articulated speaking arm, and approximate mouth shapes). Their *speech* and gesture cues use measured 48 kHz turn boundaries; pauses/narrator turns close both character mouths, and editor-only previews show the rig at rest rather than inventing timing. Frame preflight checks present/missing rig assets and clipping; an offline SVG contact-sheet tool and motion tests cover the original shapes. This is **not** phoneme-accurate lip sync or the Character Studio starter ZIP acceptance. Project-scoped individual cast voices require separate consent before any synthesis/cache hit, and commercial multi-voice output still fails closed without verified rights. **Still missing:** intentional speech overlaps (sequential turns work), custom character visual bindings + export, Character Studio-ready Pip/Quill packs and live animation inspection, syncing *dialogue turns* and nonvoice scene edits through the Rust cross-browser registry, independently rights-reviewed starter cast voices, live provider checks and UI-level narrated MP4 playback proof. Every paid attempt and actionable failure must remain visible in Jobs.
- **Embedded Production video editing (implemented UI slice; live walkthrough pending):** **Production → Create Video** mounts Director scene, dialogue-beat, asset, sound, cast, voice, preview and export controls inline. The duplicate Director sidebar route and page header are gone; the compact local video steps retain existing saved storyboards, draft renders and confirmation logic. Director remains mounted through Production steps and a Jobs & QA roundtrip, even with unsaved edits. **Still missing:** desktop/mobile/keyboard real-browser walkthrough of the new dialogue editor and its full narrated MP4, and preserved live editor state across arbitrary other sections or application reloads.
- **Character Studio onboarding (example download slice implemented):** **ZIP format and rig instructions** now includes a file tree, field-by-field importer schema guide, live JSON sample, English/Japanese help, actionable error examples, and generated downloadable `character.json` + **matching CRC-checked ZIP** with three original transparent sprite layers. The ZIP is tested against the actual production inspector; valid structure is not motion/rights approval. Built-in Pip/Quill vectors now render in video export, but Character Studio still cannot import their in-memory vector assets as ZIP packs. **Still missing:** complete rig/motion visual QA for the downloadable sprite, **Pip and Quill in the actual Character Studio starter library** with inspectable, editable ZIPs, custom rig mapping and rights review. Do not overwrite user-edited characters.

The [project voices, multi-character storytelling, embedded Production and starter-character acceptance specification](superpowers/specs/2026-10-28-project-voices-conversation-and-unified-production-design.md) defines persistence, precedence, UI flow, safety, Jobs and end-to-end verification. The **browser-local favorite/selection**, **inline Director navigation/UI**, and **Character Studio example-download/help** slices are implemented; the remaining functionality is unshipped.

If a scene is missing footage, use **Find the right visuals**, inspect a candidate's license and release requirements, and approve/import it before generating an updated version. A second or later completed draft remains confirmation-gated. Jobs records failures and retryable stages; no unfinished output is marked as a published release.

This increment tracks scene planning, visual preflight, **optional scene media search and draft media preparation**, narration, timeline, audio mix, captions, frame rendering, three Kumiki thumbnail exports, mux, quality checks, and export. A single local render worker still coordinates the stages; **media downloads, narration beats and render segments have their own separately claimed Rust Jobs attempts**, but they are not independently scheduled worker processes. Ordinary failed attempts require the user to choose **Retry draft video**. Retry rechecks current requirements and re-arms the failed Jobs node in a SQLite transaction while preserving completed step records. New Jobs store the original run UUID in immutable node input: even after a restart, a retry of the same render identity reuses individually hash-verified narration beats. Failed renders persist the exact Kumiki plan; retries verify plan/build identities, content hashes, codecs, frame counts and scene equivalence, then redraw only missing, changed or damaged H.264 chunks. The optional automatic Pexels path likewise verifies the prior run's media hash, decoder/codec/dimensions and provenance manifest before reuse. No failed segment is called a published release or skips voice authorization.

Each active production or scene attempt now renews an ownership-checked SQLite heartbeat every 20 seconds. Rust independently sweeps expired video attempts every 30 seconds (after a two-minute heartbeat timeout), even if no editor is open or another render is submitted. A retrying Node worker also asks Rust to recover expired attempts before claiming work. Live attempts remain protected from duplicate claims; stale attempts become retryable while previous successful nodes are untouched. When a worker loses ownership or the Jobs server becomes unavailable, its render signal is aborted so it cannot blindly publish output. Rust re-arms expired attempts and reconciles orphaned attempts at server startup; an authorized Node coordinator can then reclaim them as described below.

On Studio reopening, `GET /api/jobs/production/{production_id}/latest` selects the newest SQLite parent video DAG scoped by its immutable `scene-plan` input; it never returns every unrelated project/scene job. The Studio's revision-scoped status endpoint first restores an indexed, locally owned, non-symlinked draft release, then checks that Rust DAG to surface an interrupted/cancelled run with a clear Jobs/retry action. It never reclaims an attempt or implicitly reauthorizes network/voice use on a status read. New Jobs retain the nonsecret source revision for this match; legacy Jobs without one remain visible on the Jobs page. Release registration now happens *before* committing parent Jobs success, avoiding a completed-but-undiscoverable MP4 if the process exits between writes. New registrations use **one immutable UUID-owned media record per completed run** with atomic no-overwrite creation; separate Studio processes can finish concurrently without losing each other's files to a shared JSON read/modify/write race. Previous `production-media-index-v1.json` entries remain readable and untouched. Invalid legacy history is not silently overwritten. Saved media playback/downloads reject symlinked release directories and media files. Media restoration still does not replace fresh FFprobe QA for previously exported bytes.

### Automatic first draft, explicit regeneration, and startup recovery

From a saved Director scene, **Save & generate draft** applies unsaved edits and opens the full narrated MP4 path in one action; after saving, the button reads **Generate updated draft**. The first completed video for a production needs no extra confirmation. Once any completed release has been durably registered, a second or later version requires **Generate updated version** confirmation, including from the manual Export tab. Failed first attempts do not count as releases. All immutable historical release records contribute to this check, not just the newest 100 exports across the Studio. Optional online media search and voice transmission retain their independent per-session authorizations.

For real saved productions, the Node coordinator writes a private, permission-restricted render intent *before* creating the Rust Jobs attempt. The snapshot binds the exact scene revision and original user-approved voice/media settings, including the explicit multi-voice cast consent and scene assignments; it omits provider keys and unknown settings and is limited in size. The cast recovery test verifies that a restarted coordinator reuses that precise authorization and speaker voice rather than reverting to the narrator. At app startup, then every 30 seconds, it checks Rust Jobs for an actually interrupted lease (expired or reconciled after a process restart), checks the saved scene revision and current voice authorization/Keychain, repeats readiness preflight and takes a one-time atomic recovery reservation before reclaiming the same DAG and verified scene/narration caches. Two coordinators cannot both consume the same recovery allowance. A temporary readiness failure before reservation may be rechecked; a failure *after* the Jobs claim requires a deliberate retry to avoid duplicated uncertain remote voice work. Cancellation, live claims, ordinary failures and missing permissions never trigger unattended production.

Failures remain in Rust Jobs with the production job ID and bounded, actionable UI messages (including disk-full errors); stale READY nodes with ordinary failure codes appear as failed and retryable rather than as perpetually rendering. Restart recovery is **one automatic continuation per authorized run**, not an indefinite paid retry loop. It requires the Rust Jobs service, local Chromium/FFmpeg and any authorized narrator to be available. Full browser-level narration-to-MP4 proof and rich footage coverage for every scene remain separate acceptance checks.

For manifest-backed releases, the immutable release record now also retains the renderer's SHA-256 manifest digest. Before final Jobs success, Studio independently verifies the released MP4, captions, cover and all three thumbnail PNG hashes against that manifest. On restart, media listings, saved-video status and downloadable files repeat the proof before treating each artifact as valid; changed files are withheld without hiding unaffected verified assets. The video hashes are cached within a Studio process only for unchanged inode/size/mtime/ctime signatures, avoiding a full rehash for every playback range. Deleting the manifest does not downgrade a modern release to an unverified legacy one. Older production records without an export digest remain readable for backward compatibility and cannot be cryptographically verified retroactively; this is hash integrity, not a substitute for playback/codec QA.

Terminal failures record a stage-specific code and recovery instruction in Jobs, without copying raw provider diagnostics or credentials to that durable record. The Export screen exposes a single retry action. Media imports, after explicit per-asset rights approval, retry idempotent GET transfers twice on transient network/server failures (bounded backoff), but stop on rate limits, invalid hosts, media validation errors and cancellation. No partially downloaded file is registered as an approved asset.

Jobs now labels each video-production parent and child with a direct action (draft video, scene media, one-scene narration/render, or thumbnail concept) in its list and detail view, including Japanese labels. Selecting an individual child retains the scene identifier, attempt counts and failure details in its existing Jobs detail panel; background worker IDs and fingerprints are not made into user-facing workflow steps.

The existing asset discovery screens, sound library, thumbnail alternatives, rig studio, visual scene editor, and Kumiki renderer remain separate tools. **The `asset-search` node searches Poly Haven and Openverse metadata**, without calling the retired Pexels API. A creator can import a Pexels JPEG or H.264 MP4 downloaded from the website, or explicitly download one selected public Pexels photo page without an API key. Each import checks file signatures, FFprobe codec/resolution/duration, provenance, and SHA-256 before it becomes a selectable scene asset. Reviewed Pexels images/footage reach Kumiki via the user-pinned scene binding; prior pins and approved assets remain intact. This per-scene photo importer is not an unattended stock-media search crawler, and automatic download of appropriate media across an entire script is still incomplete. Kumiki generated visuals remain the fallback. Unsupported 3D models stay on Kumiki's generated fallback. Pixabay/Wikimedia/Freesound downloads and character animation are not wired as independently executable Jobs. A provider's search metadata is never treated as verified full commercial rights.

Visual scene search also includes up to eight distinct Openverse **CC0 image metadata** queries, limited to nonmature, nonwatermarked JPEG/PNG entries with usable dimensions and safe original-source links. Openverse indexes third-party assertions; its API record is **not proof of rights**, and ContentGen deliberately does not download/import these results automatically. They appear as clearly labeled reference-only suggestions with original-source and CC0 links so the editor can verify them. Combined provider matches are ranked and capped at **12 per scene**, the same limit enforced when persisted suggestions reload after an application restart. Unsupported media and provider errors retain the Kumiki fallback. Openverse image retrieval and source-authorization for automated use remain separate unfinished work. Reference: [official Openverse image data fields](https://docs.openverse.org/meta/media_properties/api.html).

When optional Pexels draft preparation encounters an unavailable or invalid top-ranked candidate, it now tries at most one different, still-eligible alternate for that scene in a separate claimed Jobs attempt. Allocation first reserves distinct primary images for all scenes, *then* assigns backups, so an earlier scene's optional fallback cannot steal the only fitting visual for a later scene. Failed candidates never become bindings; provider license/source checks, local codec/hash probes, manual pins, cancellation and the three-success download cap still apply. A **six-attempt production-wide limit** also caps the cost of failed downloads across a long storyboard (at most 80 MB per provider response), with bounded warning output. A lost Jobs completion claim stops preparation instead of concealing the ownership failure behind another download. If neither candidate passes, the scene stays Kumiki-generated.

When a tracked render fails **after** optional scene-asset discovery, its previously saved catalog can be reused on an explicit retry even across application restarts. The worker reads the original Jobs run identity, validates the owned file and production, and compares the saved shot/sound plan to the current draft before copying the catalog to the new run. Missing, invalid, symlinked, or stale saved catalogs are ignored and the bounded provider search runs again. Director reports reuse while the already-completed Jobs node retains its original historical result. Automatically prepared Pexels draft photos/footage additionally create per-scene Jobs attempts. Two independently claimed media downloads may run simultaneously, but the scheduler reserves at most three successful media slots and waits for any in-flight sibling after cancellation or a failed claim. Bindings and provenance are committed in deterministic scene order after each batch. A corrupt prior worker's media file is never reused: if the provider is available, the new attempt downloads and re-verifies the original media without altering the old file. Downloads still run under the same coordinator process rather than autonomous asset workers.

Sound Studio now offers an opt-in, bounded Openverse **CC0 music** search by mood/instrument alongside sound-effects search. Both return metadata and previews first, require checking the source plus explicit approval before local import, and re-fetch authoritative detail to verify the category. For **new videos**, music direction conservatively matches the script's subject and narration against metadata for **already imported, human-reviewed, hash-verified CC0 music**, and, if a suitable candidate exists, automatically binds one quiet full-video bed to the same render plan used for Jobs preflight and export (-34 dB, with fades). No match stays silent. The visible Sound Studio selection says whether a track is automatic, pinned by the editor, or explicitly off. Pinned music and a deliberate mute survive storyboard regeneration and remain editable; editors can return to automatic selection. The selection never automatically downloads or approves third-party sound, nor overwrites older projects' saved ambience/off intent. Automatic matching currently uses track title/tags, not audio analysis or a sophisticated soundtrack arranger. Music is never reclassified as a short sound effect or substituted in automatic shot suggestions. Audio downloads remain bounded by the approved library's file limits; long tracks must be edited externally first. This is **not** a separately resumable music-download Jobs node or a complete automatic sound director.

The actual FFmpeg master now **ducks each sustained approved music/ambience bed against the original narrator waveform** with bounded attack/release, then lets it recover during genuine spoken pauses; independent event-synced SFX remain untouched. The mastering graph explicitly returns to 48 kHz *before* sample-accurate trims to prevent FFmpeg's internal rate negotiation from shortening the finished video. Real WAV tests measure the music returning during silence, check multiple beds plus SFX, preserved sample counts and safe true peaks. A finished release records the applied compressor settings in `render-manifest.json` (`soundDucking`). This is waveform-driven ducking, not AI mood analysis or an editor-preview simulation; the Sound Studio audition still does not reproduce the final sidechain mix exactly.

Approved Openverse SFX/music GET transfers now use a shared 45-second deadline and at most three attempts for temporary network/server errors or truncated declared downloads. HTTP 429, invalid metadata, wrong licensing, cancelled requests and invalid WAV content are not retried into apparent success. Cancellation is also checked during FFmpeg normalization and before the import becomes visible in the approved sound bank. The import stays unregistered until verification, normalization and local manifest commit finish.

The exported `cover-still.png` is a verified first frame of the Kumiki render, also indexed for a direct download on the Production Export page. It is useful as a frame reference and is **separate from the three automatically generated 1280×720 Kumiki thumbnails**. Those distinct PNG and editable SVG concepts are exported into the production release and recorded in the `thumbnails` Jobs stage. Each automatic concept now has its own `video-thumbnail-concept` Jobs attempt and private source/PNG hash manifest. The three independent thumbnail conversions run concurrently with a fixed maximum of three; if one fails, in-flight concepts finish and retain their verified cache before the parent reports failure. A retry verifies finished concepts and regenerates only the missing ones. Interactive browser-side concept edits/downloads are not yet separate persisted Jobs.

When a current matching video release is available, Publish Kit now shows the **three actual render-exported PNGs together**, with a selection action and direct download for each. The first concept is the default publishing thumbnail rather than the separate first-frame still or an older browser-only draft. Existing manually selected or approved thumbnail assets stay pinned even when a newer render appears. The existing Kumiki thumbnail designer below can save/edit headlines, colors and composition and export a custom alternative without overwriting the renderer's three original PNG files; these browser-side edits still do not trigger a separate backend thumbnail regeneration Job.

The existing standalone Create → Thumbnail Composer now persists its three editable variants, active selection and palette by project/owner ID in browser storage, and reloads them after navigating away. If a saved document fails validation, it is left untouched; deliberate recovery copies the original into a timestamped recovery entry before initializing a new draft. This is **not** automatic production-specific thumbnail design or an independent Jobs stage. Publish Kit's existing thumbnail editor remains the production destination; no duplicate editor was added there.

Publish Kit's thumbnail editor now retains manual copy, artwork, palette and layout **per production and destination** when a script is regenerated. Unedited headline suggestions follow the newest script title. Matching legacy revision-scoped drafts are migrated without deleting their old copy. A corrupt saved thumbnail is never silently overwritten: controls pause until the creator explicitly backs it up and starts fresh.

In Video Director, the Narration step's **Preview selected scene voice** action now samples up to 180 characters of the active storyboard scene, rather than always playing the opening beat. The worker resolves shot-to-beat identity through the current compiled plan, rejects unknown IDs and never synthesizes the unrelated beats for this audition. Changing scenes invalidates an old audition, and explicit voice authorization is unchanged. This is an on-demand listening preview; the next full draft still uses validated per-beat narration caches for targeted regeneration.

Director's selected-scene workbench now edits the same **reveal delay, reveal pacing, camera movement and cut/fade transition** used by the real Kumiki renderer. A saved motion change only invalidates that scene's visual render; unchanged speech remains cached. Its full-preview motion editor and scene workbench share the saved state so switching between them does not create phantom unsaved changes. For a regenerated script using the **same research content**, newly saved Director sessions retain their original compiled baseline and carry forward only per-scene fields whose original values and scene roles are still compatible. Conflicting edits remain in the earlier saved script, and the newly generated narration takes precedence when its source changed. Legacy Director sessions without an original baseline still resume their exact revision, but cannot be safely transferred to a different revision.

The three existing Kumiki Publish Kit covers use **distinct, script-derived headline directions**: the overall promise, the first key section, and a different section or secondary angle. Each direction has its own editable headline and its own color treatment, plus an optional user-supplied image. **Regenerate selected concept** independently refreshes that concept's script-based headline and palette without altering the other two. Switching concepts and reopening retains the individually edited copy, color treatment and iteration count across script regeneration; untouched copy follows updated scripts. Previously saved single-headline covers migrate without losing their prior copy. The three previews are real Kumiki compositions and each exports its own PNG on demand. The backend also automatically produces three 1280×720 PNGs and tracks the `thumbnails` milestone in Jobs; one-click regeneration in the browser does not yet create a separate server-side export Job.

Provider integration should require per-result attribution/source/license metadata, restrictive download and media-type validation, optional human selection, provider-specific caching/rate limits, and manual publication review. Unsplash's API rules around image URLs and tracking are different from Pexels and Pixabay; Wikimedia Commons and Freesound carry file-specific licensing. Mixkit is typically a browsing/download catalog rather than a generic authenticated search API. Reevaluate current vendor terms before implementing automated downloads.

| Source | Practical production use | Integration caution |
| --- | --- | --- |
| [Pexels](https://www.pexels.com/api/documentation/) | Photo/footage search is already exposed by the separate scene-asset discovery tool | Require a developer API key; preserve creator/source and review the [Pexels License](https://www.pexels.com/license/) before publication. |
| [Pixabay](https://pixabay.com/service/about/api/) | Candidate photos, footage, illustration, sound | Review its [Content License](https://pixabay.com/service/license-summary/) and API limits; an API result does not certify trademarks or releases. |
| [Unsplash](https://help.unsplash.com/en/articles/2511245-unsplash-api-guidelines) | Photo search and preview | API integration requires specified hotlinked URLs, download tracking and photographer attribution; its current guidelines discourage unattended bulk experiences. Do not treat it as a drop-in offline cache. |
| [Wikimedia Commons](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia) | Historical/scientific imagery | License is per file (CC variants, public domain, etc.); store author, license version and attribution conditions. |
| [Freesound](https://freesound.org/docs/api/) | Scene-matched SFX | Filter by the actual clip's CC license and archive creator/source; avoid NC material when drafting for commercial video. |

The current automatic draft uses Kumiki-generated visual scenes, optionally illustrates reviewed Pexels assets, and uses the existing authorized sound pipeline. None of the proposed additional stock sources above is silently downloaded or marked release-ready. Video playback, seek precision, image motion and codecs still require a real Chromium/FFmpeg render smoke test on a workstation with those tools and a permitted voice source; the automated repository tests exercise the binding, freeze, server and frame-state contract with fixtures.
